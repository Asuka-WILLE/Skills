# 回归安全的功能开发

## 核心原则

新功能不是“代码能跑”就完成；完成条件是：新行为满足需求，且未被明确改变的既有行为仍然成立。

## 开始前：建立行为基线

1. 用用户可观察的语言写出旧行为：输入、输出、副作用、错误处理、性能/时序边界。
2. 标出本次有意改变的行为；其余默认是必须保持的不变量。
3. 绘制影响图：调用者、被调用者、数据结构/API、配置、持久化、异步任务、UI/CLI、日志和文档。
4. 从现有测试、样例、生产配置或可运行版本中收集基线证据；没有测试时，先补一个最小复现或验收脚本。

## 实施：让改变有边界

1. 选择最小可逆的切入点，避免顺带重构无关模块。
2. 对接口变化优先使用兼容层、默认值、版本字段或渐进迁移，而非静默改变旧语义。
3. 把新状态接入真正的执行路径；只新增变量、开关或配置而不影响实际输出，等于没有实现。
4. 明确失败路径与回滚路径，尤其是部分完成、超时、重试和旧数据场景。

## 验收矩阵

至少覆盖：

| 场景 | 要验证的事 |
| --- | --- |
| 旧输入 | 保持旧结果和副作用 |
| 新输入 | 产生目标新行为 |
| 边界/空值/错误 | 不退化为错误的默认行为 |
| 新旧混合 | 兼容逻辑不丢数据、不重复执行 |
| 失败与恢复 | 状态可恢复且不泄漏旧状态 |

## 交付格式

```text
旧行为不变量：
本次有意改变：
影响范围：
兼容策略：
已验证的新功能与回归场景：
未验证项及原因：
```
